# 頁面設計規格

> **用途**：me 各頁共用的 UI 規則，以及改頁面時逐區塊要問的檢查清單。`/site-ui-jud`（依規則挑問題）與 `/ui-draft`（直接提需求做草稿比較）都讀這份；兩支 skill 的正本在 second-brain `.claude/shared-skills/`。
> **閱讀路徑**：改任何頁面先讀〈規則本體〉與 §1；找某頁在哪讀〈頁面在哪〉；查某條為什麼這樣定讀〈沿革〉。
> **跟其他文件的分工**：頁面清單與網址以 [SITEMAP.md](./SITEMAP.md) 為準；[STYLE_GUIDE.md](./STYLE_GUIDE.md) 是旅程 App 的視覺規範；CB 資料欄位見 [CB_DATA_FLOW.md](./CB_DATA_FLOW.md)。

## 目標

- 每一頁打開就知道主角是哪個數字、哪裡可以點，不用猜資料是哪天的。
- 各頁的「這是什麼、給誰用、在哪裡用」在第一次跑 `/site-ui-jud` 時跟 Tim 確認後補在〈頁面在哪〉。

**不做什麼**：比較頁（`tools/*-draft.html`）不部署、不寫入資料。

## 規則本體

**一定要**

- 同一檔標的在同一頁的不同地方（卡片、表格、分析抽屜）顯示的價格一致，取價順序只寫一份（CB 戰情室：`watchRow.js` 的 `toWatchRow`，熱門榜 > 每日同步 > 每週價）。
- 每筆資料標出最後更新時間；今天的只寫時間，更早的加日期，只知道日期就只寫日期。
- 當天沒成交、沒有新資料的項目要看得出來（CB 戰情室：卡片反灰、寫「今天沒成交」），別讓舊價格看起來像當天的。
- 在清單裡找某一檔：打完代號就捲過去並閃框標出；它被分類或狀態篩選藏住時，先解除那個篩選再捲，不回「找不到」（CB 戰情室：工具列的搜尋框兼新增，分類下拉只在查無代號、要新增時才出現）。
- 狀態數字磚要分得開資料：幾乎永遠是 0 的狀態不單獨佔一塊（CB 戰情室：依溢價率分三段，門檻可調、存在本機；卡片左側色帶用同一套分段色，群組內依溢價率由低到高排）。
- 開發模式（`npm run dev`）不用登入就能看到真資料；正式 build 照樣要登入。
- 看得見的外觀改動，動正式頁前先照 `/ui-draft` 做左右比較頁給 Tim 選；只改字句或資料的不用。

**先問 Tim**

- 新增或拿掉一整區；改某種顏色、字型代表的意思。
- 改資料結構（Firestore 欄位、同步腳本）。

**絕不能**

- 沒讀實際畫面，就描述頁面現況。
- 比較頁或開發模式寫入正式資料而沒經 Tim 同意。

## 1. 每頁的檢查清單

改一頁之前，每個區塊依序問：

1. **讀者當下要決定什麼？** 先寫一句情境（例：「盤中決定要不要追這檔 CB」），後面六題都拿它判斷。
2. **主角數字是哪一個？** 一個區塊只有一個大數字，其他縮成小字。
3. **每一句讀完要不要猜？** 主詞寫出來；日期、數量寫到讀者能核對；資料是哪天的、從哪來的看得出來。
4. **這段字屬於哪一類？** 判讀要用的放顯眼處；查的時候才要的收起來；維護用的用小字。圖上已標出的數字，文字不再寫。
5. **同一種數字的口徑一致嗎？** 同一頁不同位置的同一個數字，來源與定義相同（例：卡片與抽屜的 CB 價）。
6. **排版有沒有帶資訊？** 並排的區塊逐列對齊；顏色只用來表示一種意思；空間有沒有浪費在不會用的東西上（例：永遠是 0 的狀態磚）。
7. **生活裡有沒有讀者已經會讀的樣子？** 這區的資料在生活裡像什麼（月曆、紅綠燈、儀表板），照它的讀法排；想不到就寫沒有，不硬套。
