# `/commit` 各步驟的由來

`.claude/commands/commit.md` 每跑一次 `/commit` 就整份讀進 context。指令檔越長，邊角的規則越容易被略過，所以指令檔只留執行時會用到的判準；「當初為什麼這樣訂」收在這裡，想改某一步時才翻。

留在指令檔的判準：**拿掉這句，執行這一步會不會做錯？** 會做錯的（觸發條件、邊界、問句寫法）留下，只說明原因的移到這裡。做法取自 second-brain 的 `knowledge/meta-evolution.md` 附錄〈`/commit` 步驟依據〉（2026-11-03 移入）。

| 步驟 | 由來 |
| --- | --- |
| **全檔** | 2026-07-06 由 `.agent/workflows/commit.md`（前代工具的流程）合併成 `/commit`（`411efd0`、`1e70933`）。2026-09-16 移植 second-brain 的設計，補步驟 0、6、7（`25b0053`）。舊版 `.agent/workflows/commit.md` 改成一行指向正本：同一個流程存兩份檔，下次就會照舊的那份做 |
| **步驟 0 規則寫回** | 只改結果、不改規則，下次跑那支指令會照舊規則再做出一次。本 repo 的指令與 workflow 多（`.claude/commands/`、`.agent/workflows/`），這是最容易漏的一步（`25b0053`） |
| **步驟 1 清理** | 原版 `.agent` workflow 就有的「動態資料不入版控」檢查，2026-07-06 合併進來（`1e70933`） |
| **步驟 3 強制綠燈** | 2026-07-06 起 guard 與 test 為綠燈基準，紅燈不提交（`1e70933`） |
| **步驟 5 改用腳本** | 2026-11-03 起由 `scripts/check-doc-sync.mjs` 判配對。起因：同日 CB 流程改版，原本的表只列了 `CB_DATA_FLOW.md`，`DATASOURCES.md` 與架構圖 JSON 是逐一 grep 才補到的。清單寫下去之後，沒有任何東西會告訴你它被跳過了；腳本跑不起來或印不出「全過」那一行，當場就知道 |
| **步驟 6 壞味道** | 2026-09-16 立六格與強制輸出的那一行（`25b0053`）。2026-11-03 把造字、主語是 AI、⚠️ 盤點三種交給 `scripts/check-smells.mjs`，其餘三種機器判不了、留給人看：硬做成檢查只會每行都報，平常就在報的檢查很快會被學會忽略。造字清單與寫檔時的 hook 共用 `.claude/hooks/coinage-list.mjs`，不再兩處各存一份 |
| **步驟 7 記憶備份** | auto-memory（`~/.claude/projects/-Users-tim-myDev-me/memory/`）在 repo 外、不受版控，機器一清就沒有。腳本遇到找不到來源或來源是空的就中止、不刪備份：來源端出錯時，照抄會把快照整批清掉。快照另開一個 commit，不跟實質變更混在一起，history 才看得出哪些是程式的改動（`25b0053`） |
| **確認問句寫「要 commit 嗎」** | 原本問「要提交嗎」。中文的「提交」也能讀成送出去給別人，2026-09-16 造成過一次混淆，分不清那一問停在本地還是會推到遠端（`53bedcf`，CHANGELOG 2.7.10） |
| **同意 commit 即接著部署（「push 要另外問」2026-11-03 推翻）** | 原本 commit 只寫本地、push 走 `/deploy` 另外問。2026-11-03 他要求回「go／允許commit」就直接 commit 並跑 `/deploy`，省掉第二次確認。問句因此改成「要 commit 並部署嗎？」，避免回答「go」卻同意了「不 push」的字面矛盾；保留「只 commit」讓還不想上線時停在本地 |
| **批准要回答那一問；打 `/commit` 不算批准** | 2026-09-16 立（`25b0053`）。打 `/commit` 的時候 diff 摘要還不存在，他不可能批准一份還沒生出來的東西 |
| **拿掉「已授權就直接提交」的例外** | 2026-11-03 推翻。當天把他說的「等 mac 這邊推上去，我在 windows 拉下來以後你再告訴我該怎麼做」讀成授權，沒問就 commit 並 push 到 main（`4d33240`）。那句話講的是之後的流程順序。有這條例外在，任何一句話都能被讀成授權，所以整條拿掉，並補上「描述之後流程的話不算批准」 |
| **`git add` 點名檔案** | 2026-11-03 立。同日用了 `git add -A`：工作區可能有別的 session 或測試留下的改動，一網打盡會一起帶進 commit。點名的清單就是 diff 摘要列的那些檔，批准的範圍和實際提交的範圍才會一致 |
| **確認點集中一節、附 diff 摘要格式** | 2026-11-03 取自 second-brain 的 `/commit`〈Checkpoints〉與〈Output〉。原本確認點夾在步驟 8 一段說明中間，摘要也沒有固定格式 |
